2026-10-30 用户调整开发联调方式：后续 App 优先连接本机编译的 Octop，便于立即验证前端修改。电脑端服务为 `http://127.0.0.1:18088`，手机通过 USB `adb reverse tcp:18088 tcp:18088` 使用同一地址。本机实例保留独立测试数据与登录账号，模型另行配置；正式服务已有验收记录继续保留。断开或重新连接 USB 后需核对端口映射。

## 2. 暂定技术路线

1. 复用 `dashboard/` 的 React 前端、业务组件、登录与 API 调用。
2. Android 首选 Kotlin + WebView 轻量容器；先做 Android 单平台所需能力，避免起步引入第二套业务 UI。
3. 初版加载受控 Octop 实例提供的网页，使页面、HTTP API 和 WebSocket 保持同源，先验证完整业务链路。界面改造后的网页需要部署到相应测试后端。
4. 前端是否随 APK 打包，在基本链路验证后再决定；若需要，再单独处理动态服务地址、跨域、授权回调及前后端版本兼容。
5. Android 代码集中在独立目录，暂定 `android/`；最终位置按克隆后的仓库结构核对。手机布局优先沿用已有 `useIsMobile`、布局与键盘适配。
6. 保留全部功能入口。常用操作优先呈现，其余模块逐页改造；阶段性的未完成项明确标记，不能按功能已完成验收。

已确认 Git、Node/npm、Python、uv、adb、Android SDK 及 `JAVA_HOME` 指向的 JDK 21 可用。Gradle 8.11.1 已下载并校验官方 SHA-256，Android 采用 Gradle Wrapper，不要求安装全局 Gradle。详见 [环境与基线](android-development-baseline.md)。

## 3. 分阶段推进与验收

### 阶段 0：仓库、环境和原版基线

工作：

- 核对工作目录、Git 状态、远程地址及各目录适用的 `AGENTS.md`。
- 配置 `origin` 指向 fork、`upstream` 指向官方仓库，记录准确基线提交。
- 遵循仓库约定：日常特性从 `develop` 创建分支。fork 当前仅有 `main`，本轮已获取并核对上游 `develop`，从该基线创建本地特性分支；不直接在 `main` 实现功能。
- 检查 Python、Node、uv、JDK、Android SDK、可用系统镜像与测试设备；先核对再补齐依赖。
- 按锁文件准备依赖，构建原版前端并启动独立测试实例，数据与生产环境分开。
- 从路由、导航、权限和实际页面整理功能矩阵，记录原版已有问题。
- 核对本项目的构建脚本与质量检查要求，建立可重复执行的 Windows 开发步骤。

验收：

- 原版可以启动、访问登录页，前端构建结果有记录。
- 功能矩阵列出页面、主要操作、角色权限、后端前置条件及预期 Android 入口。
- 已有问题和工具链缺项有明确记录；尚未验证的项目不记为通过。

交付：环境说明、功能矩阵、基线检查结果。

### 阶段 1：最小可安装 Android 客户端

工作：

- 创建最小 Android 工程与 Gradle Wrapper，先产出 debug APK。
- 提供单个 Octop 服务地址配置、地址保存、加载状态和连接错误后的重试。
- WebView 加载测试实例，验证登录、会话保持、退出和基础页面导航。
- 处理系统返回键、网页返回以及外部链接打开方式。
- 对终端、远程浏览器、远程桌面各做一次显示与基本输入的兼容性检查，尽早记录容器限制；完整交互适配放在阶段 5。

验收：

- APK 可以安装、启动、连接实例并登录；重启 App 后服务地址保留。
- 可以打开聊天、专家、设置等现有页面；返回键行为可预期。
- 服务不可达时可以修正地址或重试，无无限加载。
- 已记录复杂组件兼容性，足以决定继续使用该容器或调整方案。

交付：第一个可安装 debug APK、构建步骤与实测记录。

### 阶段 2：核心对话与常用操作

工作：

- 验证专家切换、新建会话、历史记录、流式回复、停止生成与错误提示。
- 验证工具审批的允许、拒绝与恢复执行流程。
- 接入文件选择、附件上传、生成文件下载和系统打开。
- 处理软键盘、安全区域、输入框与页面滚动，保证基础操作可用。
- 验证 WebSocket/SSE 在前后台切换后的状态，并记录需要阶段 6 加固的情况。

验收：

- 完成“选专家 → 发消息 → 审批 → 获得回复或文件 → 查看历史”的完整流程。
- 取消、拒绝、网络失败时，界面状态和后端状态可以核对。
- 文件操作使用 Android 系统机制，权限按实际需求申请。

交付：具备核心实用能力的 debug APK、流程截图与问题清单。

阶段 2 执行小计划（2026-10-30 更新，由简至难）：

1. **文字对话与输入。** 先核对正式服务可用的专家和模型，在专用测试会话验证专家切换、发送、流式显示、停止生成、历史与重新打开；同步检查真机键盘弹出时的输入框、发送按钮和滚动。本机独立实例尚未配置模型，不将其页面显示结果当作真实推理通过，也不据此判断正式服务缺少模型。
2. **附件上传。** 使用专用测试文本和图片验证系统选择、取消、再次选择、上传及消息中的附件显示，再验证多选与失败提示。已有文件选择器的容器检查不能替代聊天附件上传验收。
3. **文件下载与系统打开。** 先梳理网页实际下载方式，接入普通文件的保存与系统打开，再处理网页生成的 blob 下载。核对需要登录的文件仍遵循现有会话和权限，验证文本、图片、PDF 的文件名、类型、内容及打开行为；各小批完成后提供可覆盖安装的 APK。
4. **审批与中断恢复。** 用可控测试任务验证允许、拒绝与继续执行；补测回复期间切到后台再返回、请求失败后的界面状态，核对后端任务且不重复发送。系统级后台保活、通知和完整生命周期加固仍按阶段 6 推进。

阶段结束时按“选专家 → 发消息/附件 → 工具审批 → 获得回复或文件 → 下载打开 → 回看历史”做一轮真机串联验收。每批将实测结果写回功能矩阵，外部条件不满足的项保留待验状态。

### 阶段 3：手机导航与聊天界面

- 统一颜色、字体、间距、圆角及明暗主题，复用现有主题与国际化机制。
- 分页调整手机视图，检查桌面端的主要布局是否发生回归。

验收：

- 主要页面有修改前后的截图，竖屏及键盘弹出时操作完整。
- 功能矩阵中的入口可达，导航重排没有遗漏功能。
- 小屏与较大屏至少各验证一种尺寸，桌面端基本操作正常。

交付：首批完成手机设计的页面及视觉规范。

### 阶段 4：其余功能页面，先简单后复杂

按实际功能清单逐页推进，建议顺序：

1. 专家列表、详情、创建与基础配置。
2. 任务列表、定时任务与执行记录。
3. 工作区文件、知识库、文档上传与预览。
4. 技能、插件、专家共享、AgentTeams 和跨实例协作。
5. 连接器、OAuth 授权、MCP、通道和 ACP 配置。
6. 用户、权限、模型、存储及系统管理页面。

每批页面先验证现有操作可用，再调整表单、弹窗、列表与详情布局。具体顺序可以按阶段 0 发现的依赖修正。

验收：每一项都能从入口完成主要操作，并分别核对普通用户和管理员权限；依赖外部服务的功能有实际验证记录或明确的待验证原因。

交付：持续更新的功能矩阵、逐批可安装 APK 和页面截图。

### 阶段 5：复杂交互，逐项适配

顺序：

1. 终端：输出、输入、快捷键、软键盘、复制粘贴和横屏。
2. 浏览器 AI+：画面、点击、滚动、缩放、文本输入及连接恢复。
3. 远程桌面：画面与输入、触摸到鼠标的映射、操作工具栏及横屏。
4. 远程 Android：在后端具备 ADB 与目标设备的条件下验证现有远控流程。

验收：每种功能都在真实可用的后端环境中完成一个完整操作任务；显示和输入都验证，不以“页面能打开”作为通过标准。

交付：复杂功能实测记录、触控交互说明和对应 APK。

### 阶段 6：生命周期、通知和交付准备

工作：

- 验证断网、网络切换、锁屏、后台、旋转及进程被系统回收后的恢复。
- 返回 App 时重新核对后端任务状态，避免重复发送任务。
- 根据实际部署场景设计任务完成及待审批通知；先明确后端事件来源与传送渠道，再实现，不能依赖后台网页连接永久存活。
- 验证授权回调、系统分享、下载和前后端版本兼容。
- 整理第三方许可证及随安装包分发的内容，处理已发现的受限技能素材。
- 准备签名、版本号、安装升级与构建说明。签名密钥和模型凭据不进入仓库。

验收：

- 功能矩阵逐项关闭，有证据的通过项、未完成项和外部条件限制可以区分。
- 使用 release 构建验证安装与升级；完成适用的回归检查与真机检查。
- 发布所需的包名、最低系统版本、名称、图标和签名配置已经确定。

交付：可供最终审阅的构建产物、验收报告与交付文档。推送、创建 PR 或对外发布按届时的用户指示执行。

## 5. 质量与协作约定

- 每阶段先更新小计划，再实现最小变更，运行对应检查，记录结果后推进。
- 真机测试按用户在 2026-10-30 确定的分工执行：默认由助手指导、用户操作并反馈。每次给一个小测试，说明操作、预期结果和需要反馈的内容，收到反馈后再推进下一项手动测试。
- 真机测试效率规则（用户补充）：多个简单、相互独立且不会共享状态的单步检查可以合并成一组，一次说明、一次反馈；登录、发送、审批、后台恢复等有状态或失败影响较大的流程仍拆开指导。
- 遇到用户难以手动完成或判定的检查，由助手接手必要的 ADB、日志、像素采样或时序分析；先说明接手的检查范围，沿用已有授权执行。避免助手自动操作与用户操作同时进行；临时改动的手机设置在检查结束后恢复。
- 记录真机结果时注明来自用户反馈或助手设备检查，尚未收到反馈的手动项目保留待验。本分工针对真机验收，源码开发、构建与本机自动检查继续由助手推进。
- 前端编辑 `dashboard/`；`src/octop/dashboard/` 是构建产物，不能直接手改。
- 保留现有中英文、权限隔离、工具审批及服务端时区约定。
- Android 容器仅对受控 Octop 站点提供必要集成；外部页面交给系统浏览器，不通过全局忽略 TLS 错误解决连接问题。
- 新增连接、导航、下载和状态恢复等行为应有针对性测试；界面布局同时提供截图和设备验证。
- 遵循仓库 `AGENTS.md`：前端变更运行类型检查及构建；后端/交付检查采用 `make all`，前后端完整检查按仓库脚本执行。提交前安装仓库 Git hooks。
- Android 工程建立后运行 Gradle 构建、lint 及适用的行为测试，补充真机或模拟器验收。
- 仅文档阶段不安装整套依赖或执行业务测试；无法运行的检查写明原因，不写成通过。
- 不自动提交、推送、合并或发布；同步上游时单独检查差异，不混入当前开发任务。
